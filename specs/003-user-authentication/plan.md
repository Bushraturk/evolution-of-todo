# Implementation Plan: User Authentication & Multi-User Support

**Branch**: `003-user-authentication` | **Date**: 2025-12-28 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/003-user-authentication/spec.md`

## Summary

Implement user authentication and multi-user support for the Todo App using Better Auth (Next.js) with JWT tokens for FastAPI backend verification. This enables:
- User registration and login with email/password
- Session management with JWT tokens
- Task isolation per user (each user sees only their tasks)
- Protected API endpoints requiring authentication

**Technical Approach**: Better Auth JWT plugin on frontend issues tokens, FastAPI verifies via JWKS endpoint (stateless, no shared secret).

## Technical Context

**Language/Version**: Python 3.13+ (backend), TypeScript 5 (frontend)
**Primary Dependencies**:
- Frontend: Better Auth, better-auth/plugins/jwt, @better-auth/pg
- Backend: FastAPI, SQLModel, python-jose, httpx
**Storage**: PostgreSQL (Neon DB) - shared database for auth tables and app tables
**Testing**: pytest (backend), Jest (frontend)
**Target Platform**: Web browser (Chrome, Firefox, Safari, Edge)
**Project Type**: Web application (frontend + backend)
**Performance Goals**: Token validation <100ms, 100 concurrent authenticated users
**Constraints**: JWT expiry 15 min (access), 7 days (refresh/session)
**Scale/Scope**: Multi-user support, ~100 users initially

## Architecture Decisions

### AD-001: Better Auth over NextAuth.js

**Decision**: Use Better Auth with JWT plugin
**Rationale**:
- Native JWT plugin for external API authentication
- JWKS endpoint for stateless verification
- Active development, modern TypeScript support
- Simpler configuration than NextAuth.js

### AD-002: JWKS-based JWT Verification

**Decision**: Verify JWTs using JWKS public key (not shared secret)
**Rationale**:
- No secret synchronization between services
- Standard approach, compatible with any JWT issuer
- Public keys can be cached for performance
- More secure than symmetric key sharing

### AD-003: User ID in JWT Sub Claim

**Decision**: Extract user ID from JWT `sub` claim for task filtering
**Rationale**:
- Standard JWT claim for subject identifier
- No additional database lookup needed
- Token contains all info needed for authorization

### AD-004: Global Categories (Not User-Scoped)

**Decision**: Categories remain shared across all users
**Rationale**:
- Simpler implementation for Phase 1
- Categories are common ("Work", "Personal", "Shopping")
- User-specific categories can be added in future phase
