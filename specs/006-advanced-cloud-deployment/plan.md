**Branch**: `006-advanced-cloud-deployment` | **Date**: 2026-02-11 | **Spec**: [spec.md](./spec.md)

## Summary

Phase VI implements advanced task management features (recurring tasks, due dates, reminders, tags, advanced filtering) with event-driven architecture using Kafka/Redpanda for message streaming and Dapr for distributed application runtime. The system will be deployed locally on Minikube first, then to production cloud (Oracle Cloud OKE recommended for always-free tier). CI/CD automation via GitHub Actions enables continuous deployment.

**Key Technical Approach**:
- Event-driven architecture with Kafka-compatible message streaming (Redpanda Cloud)
- Dapr sidecars abstract infrastructure (pub/sub, state, service invocation, bindings, secrets)
- Hybrid recurring task pattern (event-driven primary + cron safety net)
- Scheduled notification system with multiple delivery channels (email via Resend, push via Web Push API)
- Extended PostgreSQL schema with new tables for recurring patterns, reminders, tags
- Microservices architecture: Main API, Recurring Task Service, Notification Service, Audit Service

## Architecture Decisions

### 1. Event-Driven Architecture

**Decision**: Use event-driven architecture with Kafka/Redpanda for all task operations

**Rationale**:
- Enables loose coupling between services
- Supports multiple independent consumers (recurring task, notification, audit)
- Provides natural audit trail
- Scales horizontally
- Aligns with microservices best practices

**Implementation**:
```
Task API → Publish event → Kafka topic → Multiple consumers
```

**Topics**:
- `task-events`: All task CRUD operations (created, updated, completed, deleted)
- `reminders`: Scheduled reminder triggers
- `task-updates`: Real-time sync for connected clients (future)

**Event Schema**:
```json
{
  "event_type": "task.completed",
  "event_id": "uuid",
  "timestamp": "ISO 8601",
  "task_id": "uuid",
  "user_id": "cuid",
  "task_data": {...},
  "metadata": {...}
}
```

---

### 2. Dapr for Infrastructure Abstraction

**Decision**: Use Dapr sidecars for all infrastructure interactions

**Rationale**:
- Abstracts Kafka, Redis, secrets management
- Enables swapping components without code changes
- Provides built-in observability (tracing, metrics)
- Kubernetes-native deployment
- Language-agnostic (HTTP/gRPC APIs)

**Building Blocks Used**:
- **Pub/Sub**: Kafka abstraction for event publishing/subscribing
- **State Management**: Redis for conversation state (existing) and caching
- **Service Invocation**: Inter-service communication with retries
- **Bindings**: Cron triggers for recurring task safety net
- **Secrets**: Secure secret management

**Sidecar Configuration**:
```yaml
annotations:
  dapr.io/enabled: "true"
  dapr.io/app-id: "todo-api"
  dapr.io/app-port: "8000"
  dapr.io/log-level: "info"
```

---

### 3. Hybrid Recurring Task Pattern

**Decision**: Event-driven primary + cron safety net

**Rationale**:
- Event-driven provides immediate response (no polling delay)
- Cron safety net catches missed events (broker downtime, consumer failures)
- Best of both worlds: responsiveness + reliability

**Primary Flow** (Event-Driven):
```
User completes task → task.completed event published →
Recurring Task Service consumes event → Calculate next occurrence →
Create new task with future due date → Publish task.created event
```

**Safety Net** (Cron):
```
Cron runs every 5 minutes → Query tasks with next_occurrence < now →
Create missing tasks → Update next_occurrence timestamp
```

**Idempotency**: Database unique constraint on (parent_task_id, next_occurrence_date) prevents duplicates

---

### 4. Scheduled Notification System

**Decision**: Scheduled notification pattern with multiple delivery channels

**Rationale**:
- Decoupled from task service (separate concern)
- Supports multiple channels (email, push, future: SMS)
- Retry logic for failed deliveries
- Audit trail of all notifications

**Architecture**:
```
Task Service → Kafka: reminders topic → Notification Scheduler →
Scheduled Notifications Table → Cron Job → Kafka: notification.send →
Delivery Workers → Email/Push
```

**Delivery Channels**:
- **Email**: Resend API (3,000/month free)
- **Push**: Web Push API (native browser, free)
- **Future**: SMS (Twilio, not in Phase VI scope)

**Retry Logic**:
- Max 3 retries with exponential backoff
- Status tracking: PENDING → QUEUED → SENT/FAILED
- Failed notifications logged for debugging

---

### 5. Microservices Architecture

**Decision**: Split into multiple services (Main API, Recurring Task Service, Notification Service, Audit Service)

**Rationale**:
- Each service has single responsibility
- Independent scaling (scale notification service separately)
- Independent deployment (update one service without affecting others)
- Fault isolation (notification service failure doesn't affect task creation)

**Services**:
1. **Main API** (todo-api): Task CRUD, user-facing endpoints
2. **Recurring Task Service** (recurring-task-service): Consumes task.completed events, creates next occurrences
3. **Notification Service** (notification-service): Consumes reminder events, sends notifications
4. **Audit Service** (audit-service): Consumes all events, maintains audit log (optional)

**Communication**: All via Kafka events (no direct service-to-service calls)

---

### 6. Database Schema Extensions

**Decision**: Extend existing PostgreSQL schema with new tables (non-breaking changes)

**Rationale**:
- Reuse existing Neon DB (no new infrastructure)
- Maintain data consistency with existing tasks
- Enable complex queries (e.g., "show all overdue tasks with reminders")
- Non-breaking: existing tasks remain unchanged (NULL for new fields)

**New Tables**:
- `recurring_patterns`: Recurrence configuration
- `reminders`: Reminder scheduling
- `scheduled_notifications`: Notification queue
- `tags`: Task categorization
- `task_tags`: Many-to-many junction table
- `task_events`: Audit log (optional if using Kafka retention)

**Migration Strategy**: Add new columns to tasks table, create new tables, add foreign keys

---

### 7. Frontend Architecture

**Decision**: Extend existing Next.js frontend with new components (no separate frontend service)

**Rationale**:
- Reuse existing component library and styling
- Maintain consistent user experience
- Progressive enhancement (new features don't break existing functionality)
- Single deployment artifact

**New Components**:
- `RecurrenceSelector`: UI for daily/weekly/monthly recurrence
- `DateTimePicker`: Due date and time selection
- `ReminderForm`: Reminder configuration (offset, channel)
- `TagSelector`: Tag management and filtering
- `TaskFilters`: Advanced filtering UI (priority, tags, due date range, search)

**State Management**: Extend existing React state with new fields (no Redux/Zustand needed for Phase VI)

---

### 8. CI/CD Pipeline

**Decision**: GitHub Actions for automated testing, building, and deployment

**Rationale**:
- Native GitHub integration (no external service)
- Free for public repositories
- Excellent Kubernetes and Docker support
- Large marketplace of pre-built actions

**Pipeline Stages**:
1. **Test**: Run unit tests, integration tests, linting
2. **Build**: Build Docker images, tag with commit SHA
3. **Deploy Staging**: Auto-deploy to staging environment
4. **Deploy Production**: Manual approval, deploy to production

**Deployment Strategy**: Rolling updates with zero downtime, automated rollback on failure

## Risk Mitigation

### Technical Risks

**Risk 1: Message Broker Complexity**
- **Mitigation**: Use Dapr abstraction, provide clear documentation, start with simple pub/sub

**Risk 2: Dapr Learning Curve**
- **Mitigation**: Provide reference implementations, start with one building block, use Dapr dashboard for debugging

**Risk 3: Event Ordering Issues**
- **Mitigation**: Use idempotent event processing, include sequence numbers, database constraints prevent duplicates

**Risk 4: Cloud Cost Overruns**
- **Mitigation**: Use Oracle Cloud always-free tier, monitor resource usage, set billing alerts

**Risk 5: Timezone Complexity**
- **Mitigation**: Store all timestamps in UTC, document limitation, plan for multi-timezone in future

### Operational Risks

**Risk 1: Deployment Complexity**
- **Mitigation**: Provide automated deployment scripts, validate deployments, provide rollback procedures

**Risk 2: Monitoring Gaps**
- **Mitigation**: Define key metrics upfront, set up alerts, provide monitoring dashboards

**Risk 3: Event Replay Issues**
- **Mitigation**: Document event replay procedures, use separate topics for testing, implement dry-run mode
