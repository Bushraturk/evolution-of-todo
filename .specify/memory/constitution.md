# Evolution of Todo Constitution

## Core Principles

### I. Spec-Driven Development (NON-NEGOTIABLE)

Every feature MUST begin with a written specification before any implementation.

- All features MUST have a Markdown specification (`spec.md`) in `specs/<feature-name>/`
- Specifications MUST define user scenarios with Given/When/Then acceptance criteria
- Implementation plans (`plan.md`) MUST be generated from specifications
- Tasks (`tasks.md`) MUST be derived from implementation plans
- No code generation is permitted without an approved specification

**Rationale**: The hackathon requires strict adherence to Spec-Driven Development methodology. Judges will review specifications, prompts, and iterations to evaluate each phase.

### II. No Manual Code (NON-NEGOTIABLE)

All implementation code MUST be generated by Claude Code from specifications.

- Direct manual coding of application logic is PROHIBITED
- Developers act as Product Architects, not code writers
- Specifications MUST be refined iteratively until Claude Code generates correct output
- Only configuration files and documentation may be manually edited
- All code generation sessions MUST be recorded in Prompt History Records (PHRs)

**Rationale**: This constraint ensures learning of AI-assisted development and demonstrates mastery of the Agentic Dev Stack workflow.

### III. Clean Python Architecture

Code structure MUST follow clean architecture principles appropriate to each phase.

- Phase I: Single `src/` directory with `models/`, `services/`, `cli/` modules
- Phase II+: Separated `backend/` and `frontend/` directories
- All modules MUST be independently testable
- Dependencies MUST flow inward (CLI → Services → Models)
- No circular imports permitted

**Rationale**: Clean architecture enables progressive enhancement across the 5 phases without major refactoring.

### IV. Test-First Development

Tests SHOULD be written before implementation when explicitly requested.

- Test files MUST reside in `tests/` directory (unit/, integration/, contract/)
- Red-Green-Refactor cycle is RECOMMENDED for complex features
- All 5 Basic Level features MUST have demonstrable acceptance tests
- Integration tests MUST verify feature completeness

**Rationale**: Testing ensures each phase delivers working functionality and enables confident iteration.

### V. Progressive Enhancement

Features MUST be implemented in priority order following the defined progression.

**Basic Level (Phase I - MVP)**:
1. Add Task - Create new todo items with title and description
2. Delete Task - Remove tasks by ID
3. Update Task - Modify existing task details
4. View Task List - Display all tasks with status indicators
5. Mark as Complete - Toggle task completion status

**Intermediate Level (Phase II+)**:
- Priorities & Tags/Categories - Assign levels (high/medium/low) or labels
- Search & Filter - Search by keyword; filter by status, priority, or date
- Sort Tasks - Reorder by due date, priority, or alphabetically

**Advanced Level (Phase III+)**:
- Recurring Tasks - Auto-reschedule repeating tasks
- Due Dates & Time Reminders - Set deadlines with notifications

**Rationale**: Progressive enhancement ensures MVP delivery while enabling advanced features in later phases.

### VI. Agentic Dev Stack Workflow

All development MUST follow the Agentic Dev Stack workflow.

- **Specify** (`/sp.specify`): Write feature specification from natural language
- **Plan** (`/sp.plan`): Generate implementation plan with technical decisions
- **Tasks** (`/sp.tasks`): Break down into testable, independent tasks
- **Implement** (`/sp.implement`): Execute tasks via Claude Code
- **Commit** (`/sp.git.commit_pr`): Automated git workflows

Each workflow step MUST produce artifacts in the `specs/` directory structure.

**Rationale**: Consistent workflow ensures traceability, enables judging of process quality, and maintains project organization.

## Technology Stack

### Phase I: In-Memory Python Console App
- **Runtime**: Python 3.13+ with UV package manager
- **Storage**: In-memory (dict/list structures)
- **Interface**: Command-line (argparse or click)
- **Testing**: pytest
- **Tools**: Claude Code, Spec-Kit Plus

### Phase II: Full-Stack Web Application
- **Backend**: FastAPI with SQLModel ORM
- **Frontend**: Next.js (React)
- **Database**: Neon DB (PostgreSQL)
- **Testing**: pytest (backend), Jest (frontend)

### Phase III: AI-Powered Chatbot
- **AI Framework**: OpenAI ChatKit, Agents SDK
- **Protocol**: Official MCP SDK
- **Interface**: Conversational natural language

### Phase IV: Local Kubernetes Deployment
- **Containerization**: Docker
- **Orchestration**: Minikube, Helm
- **AI Ops**: kubectl-ai, kagent

### Phase V: Advanced Cloud Deployment
- **Cloud Provider**: DigitalOcean Kubernetes (DOKS)
- **Messaging**: Kafka
- **Runtime**: Dapr

## Governance

### Amendment Procedure
1. Propose changes via specification document
2. Review impact on existing specifications and plans
3. Update constitution with version increment
4. Propagate changes to dependent templates
5. Document in Prompt History Record (PHR)

### Versioning Policy
- **MAJOR**: Principle removal or redefinition (breaking change)
- **MINOR**: New principle or section added
- **PATCH**: Clarifications, wording fixes, non-semantic changes

### Compliance Review
- All pull requests MUST verify compliance with constitution principles
- Phase deliverables MUST include constitution file in repository
- Specifications MUST reference applicable constitution principles
- Architecture Decision Records (ADRs) MUST be created for significant technical decisions

### Deliverables Checklist (Per Phase)
- [ ] Constitution file (`.specify/memory/constitution.md`)
- [ ] Specification files (`specs/<feature>/spec.md`)
- [ ] Implementation plans (`specs/<feature>/plan.md`)
- [ ] Task lists (`specs/<feature>/tasks.md`)
- [ ] Source code (`src/` or `backend/`/`frontend/`)
- [ ] README.md with setup instructions
- [ ] CLAUDE.md with Claude Code instructions
- [ ] Prompt history (`history/prompts/`)
